## COMPONENTS

The problem, restated: one natural-language goal, one web page, and an agent that must decide the
next action — which control, what to do to it — again and again until the goal is visible. Act 1
answers that question by asking a text LLM; act 2 answers it with Jev, a choice model over the
page's own indexed action space. The boxes are the STEPS of that loop and the artifacts each step
produces; the three UI nodes (J3) are drawn INSIDE the page and listed in the page-state.

## FLOWS

- ACT 1, one step: page → `read` → page state → `prompt` → LLM → `JSON` → executor → `run` →
  actions (cell `input` lit) → `click · input` → page. Return edge from the actions strip up to
  the page carries `× N steps` (act 1's return label; `next step` is act 2's); N is not sourced —
  the label says the letter, never a number.
- ACT 2, one step: page → `snapshot` → page state → `state + questions` → Jev → (only `TYPE_TEXT`)
  → `text?` → text helper → `{"text": "Zurich"}` → validator; Jev → `TYPE_TEXT [2]` → validator →
  `run` → actions (cell `TYPE_TEXT` lit) → `type · wait ≤ 200 ms` → page → `next step` (return
  edge). Stale page: validator → `stale → re-observe` → page state (drawn as a short dashed
  return, error family, J11).
- The worked step in both acts is the same one: the goal needs `Zurich` in `[2] Where from?`. Act 1
  ends its step with the LLM's JSON naming index 2; act 2 with Jev's target head picking `[2]` and
  the operation head picking `TYPE_TEXT`. At the two action beats (b5, b11) the page REACTS: the
  `[2] combobox Where from?` row's value goes from `San Francisco` to `Zurich` with a caret, as a
  staged overlay on the page's interior (window = that beat's hold), never a mutation of the row.

## GUARANTEE OWNERSHIP

| guarantee | owner | mechanism |
|---|---|---|
| the action space is closed: the model can only name an operation and a target that the page offered | Jev (with the page state that lists them) | choice over offered options; a probability per option; no free text (J2, J6) |
| model output never becomes a selector, a coordinate or code | validator | the target is resolved from the observed DOM node, never from the model's text (J6) |
| no action on a stale page; a retry never double-clicks | validator | fingerprint recheck before acting; a decision is consumed once (J6, J11) |
| the typed value is well-formed | text helper (checked by the validator's step) | must parse as `{"text": …}` before typing (J5) |
| act 1: the index named in the JSON exists on the page | executor | a CHECK against the live page, by the agent's own rule (B3) — not a structural guarantee; that gap is the cut's argument (G2) |

Solution audits — race: the page can change between observation and action (a suggestion list
opens, a redirect lands) → act 2 rechecks the fingerprint and re-observes on `StalePage` (J6,
J11); act 1 relies on the LLM verifying the last action next step (B3). Recovery: `MAX_STEPS`
and three no-change actions end the run as `blocked`; `DONE` still needs outside verification
(J10, J11 — sheet only). Pre-condition: a Chrome connected through Browser Harness, a TypeSafe
key and a text-model provider (sheet only).
