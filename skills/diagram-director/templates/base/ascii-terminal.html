Checkout request flow

Six components drawn with Unicode box-drawing characters on a fixed character grid. A browser sends a checkout request to the api-gateway, which forwards it over HTTP to orders-service. Orders-service reads from and writes back to redis-cache, writes orders to sql-database, and publishes an order-placed event asynchronously to message-queue; the asynchronous route is drawn with dashed box-drawing characters rather than solid ones. A thickened segment marching along a connector means traffic is flowing, a moving dot is one in-flight request, the glowing service tag is actively processing, and the shaded bar inside message-queue is queue depth, currently six of eight cells full.

  • [client] — browser, mobile, or device
  • [service] — application code we own
  • [data] — database, cache, object store
  • [async] — queue or worker (╎ ╌ dashed route)
  • [external] — third party we do not run
  • [error] — failure path
  • [infra] — platform and observability

Reading the picture: role is written into every box as a [tag] and the asynchronous route uses the dashed characters ╎ ╌ instead of │ ─, so the diagram survives a monochrome terminal, a greyscale print and a plain cat in a pipe. Reading the motion: a marching ━━ means traffic is flowing on that connector, a stepping ● is one in-flight request, the glowing service tag is actively processing, and the shaded bar is queue depth. With reduced motion enabled every one of those renders as its end state — plain connectors, the dot parked at the arrowhead, the bar at ▓▓▓▓▓▓░░ — and that end state is also exactly what you get if you select this block and paste it into a README.
