# Add A Post-Ship PR Review Loop

## Why

**Who is affected and how.** Every PR this operator ships gets reviewed by the same agent that wrote it. `ship`'s own step 4 runs quality gates, and the existing `review` skill (Phase 5, pre-ship) already delegates to Claude Code's bundled `code-review` skill — but it runs inside the same session that did the implementation, with full access to its own reasoning and justifications for why the code is fine. That is not independent review; it is the author re-reading their own diff with the benefit of already having decided it is correct. The operator has no separate signal, on any PR, from a reviewer that never saw the implementation's internal narrative.

This matters concretely for `agent-harness-kit` itself: `.agents/hooks.json`'s Antigravity cron routine (`schedule 15 8 * * 1-5`) opens PRs on `index-api`/`index-admin-cms`/`index-data` fully unattended, with no session-level self-review step at all today.

**Where it was observed.** Confirmed directly, 2026-09-18: a manual `Skill(code-review, ...)` run against merged PR #13, launched from a subagent with zero context from the implementing session, surfaced two real, verified bugs (`--rollback` leaving hook scripts on disk; an unbounded prefix match in `_entry_is_kit_owned`) that had passed the implementing session's own extensive self-testing — fixed in PR #15. This is not a hypothetical gap; it found real defects the very first time it ran, in a PR the same session had already declared fully verified.

**How this will be known to be working.** Not "the tests pass" — the tests here can only prove the wiring dispatches correctly, the same limit that applied to the hooks migration itself. The signal is: a `/ship`-created PR gets an independent findings report (Important/Nit, per the `academy.claude.com/.../ai-in-the-pr-review-loop` severity model) from an agent that received only the PR's URL and repo, nothing else — and, as with PR #13 above, that report at least sometimes surfaces something the implementing session missed. A run that always reports zero findings, forever, is not proof of quality; it is proof the reviewer isn't independent (see the scope gap below for one reason it might be).

## What Changes

- **New skill `pr-review-loop`** (Claude-only overlay skill, alongside `opsx`/`build`/`ship`): given a PR URL and its `owner/repo`, spawns a genuinely cold subagent that runs Claude Code's bundled `code-review` skill at `high` effort (never `ultra` — that requires the user's own explicit trigger and billing consent, which an automated post-ship step cannot supply) against that exact PR, applies the Important/Nit severity gate from the course's model, and reports findings back — to the session and to Slack via the kit's existing `notify-slack.sh`, **not** as inline PR comments by default.
- **`ship` skill, new final step**: after the PR is created or updated (its own step 6), spawn `pr-review-loop` as a **background** subagent — the review is advisory and does not gate the ship, which has already completed by the time review findings arrive (they can land minutes later; a real trial run took ~11 minutes). Pass the PR URL captured from that step's own `gh pr create`/`gh pr edit` output and the resolved `owner/repo`, verbatim — never let the reviewer re-derive "which PR" via `gh pr list`, which picks wrong the instant more than one PR is open (this session alone has run three PRs deep more than once).
- **Auto-commenting is built but defaults off.** `pr-review-loop` supports an explicit `--comment` mode that posts findings as inline PR comments (matching the course's "logged in the PR history" model exactly), but the kit ships it disabled by default: this kit deploys into `idx-vn/*` repos with other team members, and unattended comments on a teammate's PR from the operator's own GitHub identity, forever, on every future ship, is a materially different authorization than the operator's own Slack channel. Turning it on is a one-word change to the skill's invocation; turning it back off after comments have landed on someone else's PR is not.

## Scope gap this does not close — named, not fixed here

This only fires when the operator ships from this machine. It will never cover the Antigravity cron routine, which is the one PR-opening path with the *most* need for an independent reviewer, since it runs fully unattended. The course's actual pattern for that gap is CI-triggered (a GitHub App reacting to PR events, a check-run severity tally, branch protection requiring the review before merge) — a materially different, heavier piece of infrastructure than a `/ship`-step subagent, and out of scope for this change.
